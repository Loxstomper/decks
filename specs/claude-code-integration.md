# Claude Code integration

**Status:** decided (skill + CLI first; MCP later)

## Summary

Claude Code is the AI authoring layer. It edits `deck.html` files directly, guided by a
**skill** that documents the conventions and a small **CLI** for structural ops + validation.
The human↔AI handoff is coordinated by turn-taking over SSE.

## v1: a Claude Code skill

A skill is low-build and leans on the clean `data-*` contract. It contains:

- **Conventions doc** — the `data-eid` / `data-lay` vocabulary ([Layout vocabulary](layout-vocabulary.md)),
  folder layout ([Project structure](project-structure.md)), turn-taking model, and offline rules
  ([Principles & invariants](principles-and-invariants.md)). This teaches Claude Code to edit decks correctly by
  hand.
- **A CLI** (subcommands on the same Go binary):
  - `slides new <name>` — scaffold a deck folder (initializes the workspace if there is none).
  - `slides add-slide <deck>` — append a starter `<section>`.
  - `slides validate <deck>` — well-formedness check (see below).
  - `slides install-skill` — (re)install this skill into the workspace (see below).
  - Global `--dir <path>` / `$SLIDES_DIR` select the workspace; otherwise it is found by walking
    up from the cwd ([Project structure](project-structure.md) "Workspace resolution"). Claude Code can
    therefore run the CLI from anywhere inside a deck, and `$SLIDES_DIR` lets a hook pin the
    workspace without passing a flag.
  - `<deck>` is a name, a path to one (`decks/my-talk`, or any path inside it), or `.`. A bare
    word is always a *name*, never a relative path: from inside `decks/my-talk/`, `validate
    assets` must ask for a deck called `assets` rather than silently resolving the deck you
    happen to be standing in. Anything outside the workspace's `decks/` is refused — the CLI
    narrows to the same single-segment guard the HTTP layer uses, never loosens it.
- Claude Code edits HTML directly for content; calls the CLI for structural ops + validation.

## Skill distribution: the binary ships its own skill

**Status:** decided

The skill (`SKILL.md`) and its full contract reference (`AUTHORING.md`) are **re-encodings of the
`data-*` layout contract** ([Layout vocabulary](layout-vocabulary.md)) —
alongside the editor's `layout.ts`, the CLI's `validate.go`, the runtime `slides-layout-init.js`,
and the thumbnail's static port. A copy that drifts teaches Claude Code rules the validator no
longer enforces, which is worse than no skill at all: the deck looks authored correctly and fails
`slides validate`.

Decks live in a **workspace** ([Project structure](project-structure.md)), which is generally *not* the
slides-builder source tree — it may be a private decks repo, or any directory with a `decks/`
folder. So the skill must reach the workspace somehow, and hand-copying forks the contract.

**The binary is the carrier.** The skill and `AUTHORING.md` are `go:embed`'d into `slides` and
written into the workspace's `.claude/skills/slides-authoring/` — the same copy-into-the-workspace
pattern `Vendor()` already uses for reveal.js and the layout assets, with the same guarantee:

> **The contract the skill teaches always matches the binary that validates it.**

- **Both files install side by side**, so the skill's pointer at its contract reference resolves
  inside a workspace that has no `docs/` and is not the slides-builder repo.
- **Installed on workspace init** (`slides new` on a fresh root) and refreshed by
  `slides install-skill` — never silently on every run.
- **Idempotent and byte-stable**, like `Vendor()` / `Upgrade()`: an install that would write
  identical bytes skips the write entirely, so a decks repo that commits the skill sees no
  spurious diff and no mtime churn on every `slides new`.
- **Convergent, not merging.** An installed copy that was edited or deleted is restored to the
  canonical bytes. Preserving local edits would preserve exactly the fork this design prevents.
- **Generated, not hand-edited.** The installed copy carries a "generated by `slides`, do not
  edit — change it in slides-builder" header, mirroring the generated
  `slides-slide-themes.css`. A decks repo should `.gitignore` it or commit it knowingly as a
  build artifact.
- **The source of truth stays in slides-builder**, versioned with `validate.go` and `layout.ts`,
  so a change to the vocabulary updates the validator and the skill in one commit. It lives
  *inside a Go package* (`internal/skill/assets/`) because `go:embed` cannot reach above its own
  package directory — which is a feature here: there is exactly one copy, and it is the one
  compiled into the binary. slides-builder's own `.claude/skills/` copy is therefore a generated
  artifact like any other workspace's, committed so a fresh clone has the skill before the binary
  is built, and pinned to the embedded bytes by a test so it cannot go stale.

The same argument extends to a future MCP server (below): whatever teaches Claude the contract
should be shipped by the artifact that enforces it.

## `slides validate` (the sleeper feature)

Checks a deck is well-formed:

- valid `data-lay` values and attribute combinations,
- unique `data-eid`s,
- referenced assets exist,
- HTML parses and round-trips.

Run by **both** Claude Code *and* the editor's save path, so malformed decks are caught instead
of silently breaking the canvas.

## Targeting & change visibility

- Stable `data-eid`s let Claude Code target precisely ("rewrite slide 4 body, eid `p1`").
- The editor can **highlight what Claude changed** after an external write.

## Turn-taking handshake

1. Editor autosaves on each command.
2. Claude Code writes the file.
3. `fsnotify` detects it → server pushes an **SSE** "file changed" event.
4. Editor re-parses (guarded if mid-gesture / dirty — prompt on conflict).
5. A **status indicator** shows `synced / external change / unsaved` so the handoff is legible.

True concurrent merge is out of scope for v1.

## Later: MCP

The CLI ops (`add_slide`, `set_layout`, `insert_image`, …) become MCP tools with no redesign,
letting Claude manipulate decks via structured tools rather than raw HTML edits.
